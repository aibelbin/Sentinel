# Software Intelligence & Device Management Platform

**Requirements and architecture schema**  
**Last updated:** 2026-10-13  
**Status:** Requirements clarified; implementation details may still evolve.

> Confirmed requirements are recorded as requirements. Any remaining implementation choices are marked as open or illustrative rather than silently assumed.

## 1. Goal

Build a central platform that monitors managed Linux devices, collects installed software and system telemetry, gathers external software/security intelligence, correlates intelligence with installed versions, detects anomalies, and presents findings through a dashboard and a read-only natural-language assistant.

## 2. Initial scope

- **Operating systems:** Linux initially.
- **Software ecosystems:** Python, npm, and Java initially; design should allow additional ecosystems later.
- **Development:** Local Docker-based development, with client devices simulated using containers.
- **Deployment:** Existing VPS after local testing.
- **Dashboard:** Streamlit initially, with the backend kept independent so the frontend can later be replaced by React.
- **Backend:** FastAPI.
- **Database:** PostgreSQL.
- **Assistant interface:** A real MCP server used by an AI assistant.
- **Initial assistant permissions:** Read-only data access and predefined, approved read-only client functions; no arbitrary shell execution and no write-capable MCP tools.
- **Software updates/remediation:** Out of scope for the initial version.

## 3. Deployment and service architecture

Use one Docker Compose project to manage the platform as a whole, locally and on the VPS, with environment-specific configuration for secrets, URLs, and deployment settings. Services run in separate containers so they can be restarted independently or together.

Expected services/containers:

- FastAPI backend/API.
- PostgreSQL database using a persistent volume.
- Streamlit dashboard.
- MCP server.
- Server-side intelligence collection/processing worker.
- Predictive maintenance and risk-scoring workers or scheduled processes, isolated from the API request-handling path.

Custom services may reuse a Docker image where appropriate while running as separate containers with different commands. The aim is service isolation, not one image per component by default.

Common operations should work through Compose, including starting, stopping, restarting, viewing logs, and rebuilding the platform. For example: `docker compose up -d`, `docker compose down`, `docker compose restart`, `docker compose logs -f`, and `docker compose up -d --build`.

### Logical architecture

```text
External sources
  |  official release pages, GitHub, CVE databases, advisories,
  |  forums and other relevant technical sources
  v
Server-side intelligence collector (daily at 06:00 Asia/Kolkata)
  v
Extraction -> validation -> normalization -> intelligence store
  |                                               |
  +-------------------------------+---------------+
                                  v
                          Deterministic matching
                                  ^
                                  |
Client Linux agent --outbound HTTPS--> FastAPI <--> PostgreSQL
  |                                    |   |  |
  |                                    |   |  +--> Streamlit dashboard
  |                                    |   +-----> MCP server -> AI assistant
  |                                    +---------> processing/workers
  +-- scheduled inventory and approved on-demand functions
```

The client agent initiates outbound requests. The server does not rely on making inbound requests to client devices, which may be behind NATs/firewalls.

## 4. Client agent and installer

### Installation and enrollment

1. An administrator creates/registers a device/agent in the dashboard and obtains a unique API key.
2. The administrator provides a terminal-based installer script to the client.
3. The installer prompts interactively for the API key, installs the Python agent and dependencies, securely stores credentials, configures automatic startup with systemd, configures scheduled/background work and logging/restart behavior, registers with the backend, and verifies connectivity.
4. The agent's key is stored in a restricted-permission configuration file (for example, mode `600`) accessible only to the account running the agent.

### Identity and authentication

- Every agent has a unique ID generated by the platform and linked to its API credential.
- Hostname and OS details are metadata, not primary identity.
- Each device uses its own API key; keys can be revoked or regenerated.
- Administrators can temporarily disable an agent.
- Identity rotation/reassignment must preserve configuration and historical continuity through an explicit rotation/reassignment record. Do not merge history solely because mutable host metadata matches.
- Agent API requests use HTTPS and device-specific authentication.

### Heartbeat, inventory and task polling

These are distinct responsibilities:

- **Heartbeat/task/config polling:** Every 60 seconds by default, the client initiates an HTTP request to FastAPI to ask for queued jobs and configuration changes. The polling interval can be changed through backend-delivered configuration.
- **Inventory collection:** Runs twice daily by default. Its schedule/interval is configurable through a backend config task. It is independent of the 60-second heartbeat.
- **Reporting:** After a collection or task completes, the agent sends the report/result to FastAPI.
- **Offline behavior:** The agent queues reports, detectable software changes, logs and task results while offline and uploads them after connectivity returns. Each report includes its timestamp; the server uses timestamps to reconstruct history. The client does not need to implement server-side timeline stitching.
- **Local queue limits:** Retain queued data for up to 30 days, subject to a configurable disk-size cap. The exact initial cap and behavior when limits are reached remain implementation details to define.

### On-demand tasks

The backend queues on-demand requests. Agents discover them on their next poll, execute only predefined approved local functions/tools, and submit results. Tasks have unique IDs and statuses such as `pending`, `running`, `completed`, and `failed` to reduce duplicate execution and support recovery after interruptions/restarts. Manual local triggers may also run approved functions and report results.

No arbitrary shell commands or LLM-generated commands may be executed. Validate tool parameters and use least privilege.

### Data collected

- OS and host details.
- System resource information.
- Installed applications/software.
- Python, npm, and Java versions and package/dependency inventory.
- Detectable package/software installations, removals, and version changes.
- Task results and relevant logs.

Exact inventory payload fields/API contracts can be finalized during implementation.

## 5. Server-side schedules and processing

### Intelligence collection

- Run daily at **06:00 Asia/Kolkata (IST)** on the server, not on client devices.
- Collect, extract, validate, normalize and store intelligence.
- Match newly collected/updated intelligence against all reported device inventories.
- Generate a daily summary available in the dashboard after processing.
- Email notifications are not in scope initially.

### Inventory-triggered matching

When a new inventory report arrives, immediately match that device's inventory against the intelligence already stored. Matching therefore happens both when new intelligence is processed and when new inventory arrives.

### Background processing

Scheduled and potentially long-running collection, matching, and ML jobs should run outside FastAPI request handling, in separate worker/scheduled processes or containers. FastAPI remains responsible for API requests, task/config delivery, and receiving reports.

## 6. Software intelligence pipeline

### Sources

- Official release pages.
- GitHub.
- CVE databases.
- Official and vendor security advisories.
- Relevant forums and other technical sources.

### Source management

The dashboard includes an Intelligence Sources tab where administrators can add sources and configure attributes such as:

- Official developer source.
- Maintained by software vendor.
- Official security advisory.
- Community-maintained.
- Verified source.

The exact labels may evolve. An authenticity score is automatically derived from selected attributes, with administrator override available. Source priority is configured separately as Low, Medium, or High.

### Extraction and validation

1. Collect source content.
2. Extract software/package identifiers, affected-version ranges, fixed versions, source-reported severity/CVSS, dates, and references/evidence where available.
3. Prefer deterministic parsing for structured sources.
4. Use an LLM to interpret unstructured content where useful.
5. Validate extracted claims and preserve source references/evidence.
6. Normalize and store the records.
7. Match affected-version ranges to reported inventories using deterministic rules.

The LLM must not decide whether a specific installed version is vulnerable. If version data or evidence is missing/ambiguous, mark the result Unknown and preserve evidence rather than guessing.

Preserve each source's reported severity and CVSS. If sources disagree, retain the individual assessments; do not derive a single unified severity initially.

### Record history and retention

- Keep the latest record for each advisory and preserve changes to fields such as severity, affected versions, and fixed versions.
- Preserve timestamps, source references and evidence.
- Retain software intelligence records and their change history for **90 days**.

## 7. Vulnerability findings

Vulnerability findings have a dedicated, isolated dashboard tab with these statuses:

- **New:** Recently discovered finding.
- **Active:** Confirmed as affecting the device.
- **Resolved:** No longer affected based on updated inventory or intelligence.
- **Unknown:** Insufficient or ambiguous evidence to determine applicability.

When a device reports a fixed software version, automatically mark the finding Resolved while preserving its history. Findings should be filterable/sortable by severity, affected devices, source priority, and status. Matching must remain deterministic and evidence-based.

## 8. Dashboard and device detail

Use separate tabs to avoid overloading a single page. Planned tabs/modules:

- Overview.
- Vulnerabilities.
- Daily Findings.
- Devices.
- System Health.
- Anomalies.
- Predictive Maintenance.
- Risk Prediction.
- Intelligence Sources.
- Logs & History.
- Settings.
- AI assistant via MCP.

A device detail page should combine inventory, vulnerability findings, system health, anomalies, and historical changes. Task history should show requested operations, status, timestamps, and results.

### Device last-seen status

Use the 60-second heartbeat to derive device status:

- **Online:** Heartbeat received recently.
- **Stale:** Heartbeats missed beyond a configurable threshold.
- **Offline:** No heartbeat received beyond a longer configurable threshold.

The exact thresholds are configurable implementation details; a single missed heartbeat must not immediately mark a device offline.

## 9. Anomaly detection

Anomaly detection runs lightweight checks for unexpected package/software installations, removals, version changes, and significant inventory differences. It may flag large bursts of changes using configurable thresholds (for example, more than 20 package changes between reports; the number is an example, not a finalized default).

For each device, automatically establish a baseline from its first few inventory reports. Compare subsequent reports against that baseline to detect deviations. Normal changes may gradually update the baseline automatically; significant deviations are flagged for administrator review rather than silently becoming normal. An anomaly is suspicious, not proof of compromise.

## 10. Predictive Maintenance

This is a separate, isolated dashboard module and must not interfere with other components. Initially use existing ML algorithms/models trained on relevant public datasets, then consider improving them with telemetry collected by this platform.

Initial target areas, using separate models:

1. Dependency conflicts and compatibility (primary focus).
2. Software crashes and recurring failures.
3. Resource-related issues (CPU, memory, disk).

Initial ecosystem focus is Python, npm, and Java. Predictions run daily initially. Additional runs after significant changes may be considered later. Exact public datasets, model selection, evaluation criteria, and serving contracts remain implementation work.

## 11. Risk Prediction

Risk Prediction is a separate, isolated, advisory-only module. It must not trigger actions or modify any system component.

- Initially use EPSS plus transparent device-level risk scoring; no separate ML model is required initially.
- Consider installed software and affected versions, known vulnerabilities, EPSS exploit likelihood, severity, and evidence.
- Display a score from 0–100, a Low/Medium/High/Critical level, contributing factors, and an explanation.
- Explain that the score is advisory and not proof of compromise. EPSS represents exploit likelihood for a CVE, not the probability that a whole device will be compromised.
- Recalculate daily, when new inventory arrives, and when new vulnerability intelligence is processed.
- Store daily historical score snapshots and additional snapshots when the score or risk level changes.

## 12. MCP assistant and approved tools

Use an actual MCP server. The administrator interacts with the tools through the AI assistant; a separate manual tool-selection interface is not required. Task history remains visible in the dashboard.

### Flow

1. Admin asks the assistant a natural-language question.
2. The model selects a predefined approved MCP tool.
3. MCP/backend checks scope and queues a task if client execution is needed.
4. The client retrieves the task during its next poll and runs the predefined function.
5. The client posts the result to FastAPI.
6. The assistant presents the result.

The assistant can query all platform modules, including inventory, vulnerabilities, health, anomalies, predictive maintenance, risk scores, and logs. Fleet-wide questions (for example, which devices run Python 3.10) should be supported. Per-system settings define the allowed data and operation scope.

Illustrative predefined read-only tools include `get_system_info`, `get_software_inventory`, `check_package_version(package_name)`, `get_resource_usage`, `get_service_status`, and `get_recent_logs`. Exact names and schemas are implementation details. The LLM cannot generate arbitrary commands or scripts.

### Audit

Record MCP tool invocations centrally on the server, including administrator request, selected tool, target device, execution status, timestamps, and returned result. Retain MCP audit logs for **30 days**.

## 13. Authentication, authorization and security

- One system administrator account with full access; multiple admin roles are not required initially.
- Dashboard admin authentication is separate from device authentication.
- Admin login uses password authentication only initially; **no 2FA**.
- Password recovery is performed manually on the VPS; no email-based recovery flow initially.
- Device API keys are unique per agent, sent only over HTTPS, and can be revoked or regenerated.
- Store agent credentials in a restricted-permission file readable only by the agent's running account.
- Agents can be temporarily disabled and can rotate identity while preserving configuration/history through an explicit record.
- MCP tools use predefined operations, validated inputs, scope restrictions, and least privilege.
- No arbitrary remote shell execution, arbitrary LLM-generated commands, automated remediation, or software-update execution.

## 14. Database and history retention

PostgreSQL is the central database. Store inventory snapshots and software-change history so changes can be reconstructed over time. Each report includes a timestamp, and the server stitches historical data together.

Retention requirements:

- **30 days:** Operational logs/history, inventory history/snapshots, and MCP audit logs.
- **90 days:** Software intelligence records and their change history.
- **Risk history:** Daily score snapshots plus additional snapshots when the score/level changes; a separate retention period has not been specified.
- **Offline client queue:** Up to 30 days, subject to a configurable disk-size cap; exact cap/overflow behavior remains to be set.

## 15. Testing and rollout

- Begin with local Docker-based testing and simulated Linux client containers.
- Use automated unit tests and integration tests from the beginning, along with manual testing.
- After local testing, deploy the same Docker Compose project to the existing VPS using environment-specific configuration.
- Add end-to-end and simulated network interruption/reconnection tests as the implementation matures.
